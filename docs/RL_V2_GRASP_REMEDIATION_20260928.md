# Multi-box v2 양손 flap 파지 SAC 개선 보고서 (2026-09-28)

## 범위와 기준

S63 + Leju two-finger, 24차원 upright-torso SAC의 새 학습 설정이다. 두 손이
서로 다른 flap을 잡고 proof lift 8 mm를 0.25 s 유지하는 성공 조건, 랙
10 N·기타 장애물 5 N 충돌 종료, 현재 무작위 박스 reset 조건은 바꾸지 않았다.
curriculum도 추가하지 않았다. 아래의 기존 실행 수치는 수정 전 실행의 기록이며
이번 코드의 성능 결과가 아니다.

기존 GPU 3 실행 `mbv2_upright_sac_gpu3_20260928_174257`의 135 iteration
기록: 유효 전이 6,976,971건, SAC 업데이트 16,052회, 한 손 파지·양손 파지·
성공 이벤트 모두 0회. 마지막 iteration의 안전 위반 종료 15건 중 랙 9건,
기타 장애물 6건. alpha는 0.01 하한에 도달했다. 시작 시 사용한 워밍업은
180 vector step, 6-step action hold, continuous scale 0.5였고 데모를
고정 25%로 critic replay에도 섞었다.

## 확인된 문제와 수정

| 문제 | 이번 수정 | 검증 기준 |
|---|---|---|
| 성공 경로와 무관한 독립 난수 워밍업 | 데모가 있으면 rollout 전에 actor-only BC 1000 update를 수행하고, 워밍업에서는 그 actor의 관측 피드백 행동에 시간 상관 잡음(기본 scale 0.12)을 더한다. 환경별 종료 시 잡음을 초기화한다. 데모가 없을 때의 기존 난수 워밍업은 유지한다. | 실제 rollout에서 랙 앞 도달률, 두 손의 10 cm 도달률, 충돌률 비교 |
| 가까워지기 전에 무작위로 닫는 그리퍼 | 배정 flap 중심으로부터 0.12 m 밖이면 워밍업·온라인 정책·critic 목표 행동·checkpoint 재생 모두 그 손을 열어 둔다. 차단된 그리퍼 차원은 entropy에서도 제외한다. 그리퍼 채널에 탐색 잡음을 넣지 않는다. | `grasp/*_premature_close_fraction`, 실제 파지율 |
| 데모 0=open/1=close와 SAC 부호식 action의 불일치 | 변환된 데모의 gripper action과 이전 action 관측을 -1=open/+1=close로 바꾼다. 변환 버전을 manifest에 기록한다. | 데모에서 열린 상태를 잘못 닫는 비율과 오프라인 BC 닫기 정밀도 |
| 옛 보상을 새 critic에 섞는 문제 | 데모는 actor 모방에만 사용하고 critic은 현재 환경에서 수집한 reward만 사용한다. 데모 배치 비중과 모방 손실 계수는 0.2에서 시작해 계획된 SAC 업데이트의 첫 30%에 걸쳐 0으로 줄인다. | 데모 reward를 바꿔도 동일한 critic/actor 업데이트가 나오는 CPU 테스트 |
| 접촉 없는 그리퍼 간격 보상 | jaw-gap 양의 보상 가중치를 0으로 바꾼다. 실제 접촉 검사에 통과한 one-hand/bilateral pinch 이벤트는 유지한다. | gap reward 0, pinch event와 성공 event의 분리 기록 |
| 랙 앞 진입과 최종 접근 신호 부족 | 손별 배정 flap의 랙 앞 안전 평면 위치를 향하는 `front_staging` 보상 1.0과 넓어진 flap 접근 보상 2.0을 추가했다. 진입하면 stage 점수가 떨어지지 않도록 깊이를 포화시킨다. | `front_staging_progress`, 손별 front/flap 거리 및 10 cm 이내 비율 |
| 파지 직전 실패 원인 식별 불가 | pre-reset 물리 상태에서 손별 pinch, 순간 성공 조건, 손별 그리퍼 닫기·조기 닫기, 몸통 pitch·관절 추종 오차를 iteration별 기록한다. 기존 충돌 원인·힘 구간 기록은 유지한다. | 첫 파지 실패가 도달·닫기·접촉·유지 중 어느 단계인지 분해 |
| 데모 몸통 action 근사 변환 | 변환 시 X/Z action 포화 비율과 버린 waist-pitch 명령 평균을 기록한다. 이전 세 축 제어를 현 두 축 제어로 정확하게 재생할 수는 없다. | 실제 Isaac에서 변환 action 재생과 몸통 추종·파지 결과 확인 |

보상과 관측의 랙 기준 좌표·두 flap 배정은 기존 테스트로 확인했다. 기존
성공 조건을 약화시키지 않았고, self-collision은 학습 실행 옵션에 따른다.

## 수행한 검증

- CPU 테스트 89개 통과, `git diff --check` 통과. 테스트는 데모 변환,
  양손 할당/보상, SAC 데모 reward 격리, BC 사전학습, 유도 워밍업 그리퍼
  거리 gate, 종료 전 관측 보존을 포함한다.
- 성공 데모 2개(910전이)를 현재 440차원 actor/24차원 action으로 변환했다.
  두 축 torso action 포화 비율은 2.31%, 제거된 waist-pitch 명령의
  평균 절댓값은 0.000297 rad/step이다.
- 두 데모 전체에서 actor를 1000 update 학습한 **학습 데이터 내**
  MSE는 0.282→0.0217, 닫기 재현율은 좌/우 96.6%/95.0%, 정밀도는
  98.2%/100%였다. 수정 전 0=open을 그대로 MSE target으로 사용하면
  두 손의 닫기 정밀도가 약 12%로 떨어졌다.
- 데모 하나만 학습하고 다른 하나를 평가하는 제한적 교차 검증에서는
  MSE 0.629 또는 0.418, 닫기 재현율 0% 또는 77.6%였다. 초기 상태·
  박스 배치 일반화가 확보됐다고 볼 수 없다.
- GPU 0, 4환경, 96 control step(환경당 3.2 s)의 짧은 Isaac 검증을
  두 번 완료했다. 첫 실행은 워밍업 게이트만 적용해 워밍업 이후 먼 거리
  닫기 비율이 좌 23.4%·우 22.9%로 드러났다. 이를 반영해 전 학습·재생
  경로에 게이트를 적용한 두 번째 실행에서는 양손 닫기·조기 닫기 비율이
  모두 0이었다. 유효 전이 384건, 비유한 전이 0건, SAC 업데이트 47회,
  충돌 종료 0건, 접근·랙 앞 진입 보상 양수, 몸통 pitch 오차 평균
  0.00339 rad·최대 0.00967 rad였다. 이는 짧은 배선 검증이며 파지
  성공률 검증이 아니다. 두 번째 실행에서는 두 손 모두 10 cm 이내에
  들어오지 않았으므로, 가까운 상태에서 정상적으로 닫는 동작은 CPU
  거리 gate 테스트로만 확인했다. 두 성공 실행의 checkpoint·manifest·metrics·
  status를 기존 `seonho:HumanoidScene-RL`에 크기·MD5 검증 업로드했다.
- 두 번째 실행의 checkpoint를 CPU에서 복원해 action projection 계약과
  모든 출력의 유한성, 먼 목표에 대한 두 그리퍼의 열린 명령을 확인했다.

## 남은 검증과 데이터 의존성

이번 작업은 위 3.2 s 배선 검증을 제외한 장기 학습이나 성공률 평가를
실행하지 않았다. 따라서 충돌 없는 전체 진입 경로, 새 보상에 따른 학습
개선, 실제 양손 파지 성공을 아직 주장할 수 없다. BC actor는 상태
피드백을 쓰지만 충돌 회피 플래너가
아니다. 두 성공 데모만으로는 다양한 reset 배치에 대한 충분한 증거가
없으므로, 현재 24차원 제어와 관측 계약으로 VR 성공 데모를 추가 수집해야
한다. 특히 각 박스 위치·높이·flap 배정별로 성공과 안전한 실패 복구
사례를 확보하는 것이 다음 데이터 작업이다.

다음 실험은 다른 사용자의 프로세스를 건드리지 않고 고유 실행 폴더와
`CUDA_VISIBLE_DEVICES`를 사용한다. 데모 변환 행동의 재생·몸통 추종
오차·랙/장애물 충돌을 먼저 보고, 이어서 새 설정의
짧은 SAC pilot에서 `front_staging` → 손별 접근 → pinch → 성공 순서로
지표가 오르는지 확인한다. 단계가 정체되면 해당 단계의 관측·데모 분포를
보강한다. Drive 백업이 필요한 실행은 `docs/RL_GOOGLE_DRIVE.md`의 기존
연결과 검증된 체크포인트 보관 절차를 따른다.

이번 변경은 작업 트리에 있으며 기존 실행 중인 프로세스에는 적용되지 않는다.
새 보상/데모 계약으로 이어 학습할 때는 별도의 새 실행을 사용한다.
